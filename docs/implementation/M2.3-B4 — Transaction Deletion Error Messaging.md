# M2.3-B4 — Transaction Deletion Error Messaging

**Status:** Accepted
**Scope:** Transactions Screen — Correction / Deletion
**Decision Type:** UI Behavior / Deferred Improvement

## 1. Context

During M2.3-B4, the transaction deletion flow was reviewed to determine how deletion failures should be communicated to the user.

The Financial Engine may return:

- `OperationRejected`
- `DomainViolationResult`
- Other unsuccessful results
- An exception during execution

Both `OperationRejected` and `DomainViolationResult` contain a `reason` string. However, these reasons originate from Policy and Domain layers and are not guaranteed to be user-facing or localized messages.

## 2. Decision

The Transactions Screen will display a generic localized error message whenever a deletion attempt fails.

**Arabic:**
> تعذر حذف العملية. حاول مرة أخرى.

**English:**
> The transaction could not be deleted. Please try again.

Raw `reason` values must not be displayed directly to the user.

Technical details may remain available through application logs for debugging.

## 3. Expected Behavior

| Scenario | User-facing behavior |
|---|---|
| Deletion succeeds | Refresh the transactions list without showing an error |
| Deletion is rejected by a domain or policy rule | Display the generic localized error |
| Deletion fails due to a technical exception | Display the generic localized error |
| User retries and deletion succeeds | Refresh the list without showing an error |
| User retries and the underlying rejection persists | Display the generic localized error again |

The error message is associated with each failed attempt. It is not a permanent notification.

## 4. Deferred Improvement

A future task should introduce explicit error classification and user-facing message mapping.

The future implementation should distinguish between:

1. **Domain / Policy Rejection:** A financial or business rule prevents deletion.
2. **Transient Technical Failure:** A temporary execution or infrastructure problem prevents deletion.
3. **Unknown Failure:** The cause cannot be reliably classified.

Each category should map to an appropriate localized message.

The application must not depend on displaying raw internal `reason` strings.

## 5. Scope Exclusion

This improvement is deferred and is not part of M2.3-B4.

M2.3-B4 remains limited to:
- Generic localized deletion failure messaging.
- Preventing duplicate deletion requests while a request is in progress.
- Refreshing the transaction list only after successful deletion.

No changes to Financial Engine rules, domain behavior, or financial data integrity are required by this decision.

## 6. Acceptance Criteria

- [ ] Arabic and English generic messages are displayed correctly.
- [ ] Raw Domain and Policy reason strings are never exposed in the deletion SnackBar.
- [ ] Successful deletion does not display an error.
- [ ] A subsequent successful retry clears the failure condition through normal list refresh.
- [ ] Persistent rejection produces the same generic message on each failed attempt.
- [ ] Detailed error classification remains a separate future task.
